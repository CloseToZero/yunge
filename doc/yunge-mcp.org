#+title: Yunge MCP

Yunge MCP exposes selected Emacs capabilities to local AI clients through a
typed Model Context Protocol interface.  The native executable implements the
stdio protocol and forwards only registered tool calls to the running Yunge
Emacs.  Emacs owns tool definitions, editor state, and application semantics;
the executable does not evaluate caller-supplied Lisp or access application
databases itself.

The minimal tool set belongs to Fangcun:

- =fangcun_list_yiyus= lists the configured note roots by identifier,
  display name, and absolute root path.
- =fangcun_search_nodes= searches node titles, aliases, tags, yiyu names, and
  relative files.  Results are ranked by match quality and use opaque cursor
  pagination.
- =fangcun_locate_node= returns one node's absolute file, line range, outline
  path, and unsaved-buffer state without returning its content.
- =fangcun_list_backlinks= returns unique source nodes linking to one node,
  together with each source's occurrence count and first link position.  It
  uses opaque cursor pagination and does not read note content.
- =fangcun_create_file_node= creates, saves, and indexes a new Org file node;
  its =file= argument is a path relative to the selected yiyu root, and missing
  parent directories are created.  It writes the file-level ID and optional
  title; agents add note content afterward with their filesystem tools.
- =fangcun_create_heading_node= gives an existing heading a local =ID=, then
  saves and indexes it.  The heading is selected by its exact outline path;
  existing IDs are retained, just like =SPC n c=.

Heading paths run from the outermost heading to the target and use heading
titles without TODO keywords, priorities, or tags.  A missing or ambiguous
path is rejected.  The file-node tool generates a file-level ID while creating
the file, so a new note is never temporarily an unindexed plain Org file.  Both
ID tools index their saved result before returning.  The heading tool refuses
to save a file whose visiting Emacs buffer already has unsaved changes.

* Direct file workflows

Fangcun yiyus contain ordinary Org files.  When those files are accessible to
the MCP client, the client uses its own filesystem tools for reading, literal
full-text search, inserting or deleting links, and general content edits.
=fangcun_locate_node= bridges semantic node discovery to those tools without
copying note content into the model context.

Fangcun watches its configured roots and updates the index after saved external
changes, so direct file edits do not require an MCP synchronization call.  Use
the MCP tools only for root discovery, indexed node search, node locations,
semantic backlinks, and ID-bearing node creation.

Agents write standard Org links and targets directly.  An ID link is
=[[id:NODE-ID][DESCRIPTION]]= or the bare =[[id:NODE-ID]]= form.  To jump to a
named target inside that ID node, use
=[[id:NODE-ID::target][DESCRIPTION]]= and define =<<target>>= there.  A
standalone target link is =[[target][DESCRIPTION]]= or =[[target]]=.  A radio
target is =<<<radio target>>>=; later exact plain-text occurrences in the same
document become links automatically.  Fangcun needs no separate tool for these
or for other ordinary Org link formats.

* Search and backlink pagination

Both =fangcun_search_nodes= and =fangcun_list_backlinks= accept =pageSize=
between 1 and 100, defaulting to 20.  When more results exist, the response
contains an opaque =nextCursor=.  Pass that value back as =cursor= with the
same query or target ID to read the next page.  A response without
=nextCursor= is the final page.

Search requires every whitespace-separated query term to match.  Results
prefer exact title or alias matches, then prefixes, word and substring
matches, tags, relative files, and yiyu identifiers or names.  Ties have a
stable node order.  Each result reports =matchedFields= so a caller can see
why it matched without depending on an internal numeric score.

Backlinks are paged by unique source node rather than individual link
occurrence.  Repeated links in one source produce one result containing
=occurrenceCount= and =firstPosition=.

Run =M-x yunge-mcp-setup= to build and install the server, then declare it in
the user configuration of selected AI agents.  The prompt always lists every
supported agent; an agent need not be installed before it is selected.
The initial clients are Codex, Claude Code, Gemini CLI, Cursor, and the default
Visual Studio Code profile.

The installed executable has the stable path
=var/yunge-mcp/bin/yunge-mcp=, with the platform's executable suffix where
required.  Agent declarations keep pointing to this path when the server is
rebuilt.  Existing agent configuration is retained; setup owns only the MCP
server entry named =yunge=.

Use =M-x yunge-mcp-install= to rebuild without changing agent configuration,
or =M-x yunge-mcp-register-agents= to change declarations without rebuilding.
The bridge protocol and runtime manifest are documented in
[[file:../native/yunge-mcp/README.org][the native bridge documentation]].
