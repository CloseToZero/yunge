#+title: Yunge Reader

Yunge Reader is an extensible Emacs document reader.  PDF is the first
backend, but the core models ownership, location, selection, and view state
without assuming that every document consists of immutable pages.

* Current PDF slice

Run =M-x yunge-reader-native-setup= once, then open a PDF explicitly with
=M-x yunge-reader-pdf-open=.  Yunge Reader deliberately does not add an entry
to =auto-mode-alist= while the reader is under development.

The current PDF adapter provides:

- verified PDFium installation and a locked Rust helper build;
- open, close, page count, labels, and complete page geometry;
- a continuous, virtualized page roll with bounded image residency;
- next, previous, direct page, screen, mouse wheel, and ordinary scrolling;
- fit-width, fit-page, and bounded manual zoom;
- canonical bounds and rotated glyph quadrilaterals for local hit testing;
- cross-page drag, polygonal SVG highlights, and exact text copying;
- bounded Unicode literal search, repeat navigation, and glyph-level jumping;
- versioned per-document places with zoom-aware PDF viewport restoration;
- immutable render keys, stale-response rejection, and bounded disk cache
  eviction; and
- graceful, forced, idle, EOF, and Emacs-exit service shutdown paths.

The reader uses one key vocabulary with or without Evil.  Shared keys are
=y= to copy the logical selection, =/= to start a search, =n/N= to visit the
next or previous match, =gr= to refresh, =+/-= to zoom, === to reset zoom,
=W/P= to fit width or page, and =q= to quit.  PDF views use =J/K= for the
next or previous page, =gg/G= for the first or last page, =gp= for a page
prompt, and Page Down or Page Up for screen scrolling.  Evil starts Reader
buffers in Normal state and leaves Visual =y= as =evil-yank=.
=M-x yunge-reader-clear-search= removes the active match highlight.

* Library boundary

The implementation is divided into four pieces:

- =yunge-reader.el= owns drivers, documents, stable positions, logical
  selections, bounded search state, reader buffers, and zoom state.
- =yunge-reader-native.el= owns subprocess requests, build identity,
  reference counting, cache policy, idle shutdown, and explicit lifecycle
  commands.
- =yunge-reader-setup.el= owns the pinned engine manifest and verified,
  operation-private installation transaction.
- =yunge-reader-pdf.el= maps the format-independent interface onto PDFium,
  virtualizes a continuous page roll, and paints visible selections.

The core never depends on PDFium, PDF page objects, or PNG.  A driver supplies
a name, file matcher, open function, close function, and request function.
Open and request completion may be immediate or asynchronous.  The core
guards completions so one driver mistake cannot complete an operation twice.

Opening a document declares one of two layouts:

- =fixed= documents have stable spatial units, normally pages.  PDF, DjVu,
  XPS, and comic archives fit this model.
- =reflow= documents derive line and page breaks from the viewport and
  typography.  EPUB, HTML, and plain text fit this model.

This prevents an EPUB backend from having to imitate permanent PDF pages and
prevents the PDF backend from pretending its glyphs are ordinary Emacs buffer
text.

* Locations, selection, and later annotations

A =yunge-reader-position= contains a document unit, a stable text offset or
driver anchor, and optional unscaled coordinates.  PDF coordinates remain in
the page coordinate system; zoom only changes their screen projection.  A
reflowable backend can instead store a spine item and CFI-like anchor.

The core persists a bounded, most-recently-used place alist through
=savehist=.  Each value is plain printable data containing a format version,
driver name, stable position, zoom mode, and manual scale.  It does not
serialize Lisp structures that may be undefined when =savehist= first loads.
A driver that supports places supplies location and restore functions as a
pair.  Future reflowable drivers can use the same contract without storing an
Emacs buffer point.

Opening treats an old place as pending data.  Place recording remains disabled
through native document opening, the initial view refresh, and restoration.
Only a successful restore permits the current view to replace the old record.
An unavailable or unbuilt helper, an open or refresh failure, an invalid
layout, or a rejected restore therefore leaves the prior place untouched.  In
particular, a transient initial PDF page zero cannot become durable state.

PDF places store a zero-based page and the canonical page coordinates visible
at the viewport's top left.  Zoom state is restored before building the view;
the coordinates are then projected into the current render size.  A page past
the new document end is clamped to the last page.  If the Reader buffer has no
live window, the PDF adapter retains the position and applies it before the
next visible-page update and before recording any replacement.

A logical selection contains two positions and optional resolved text.  Its
painted rectangles are disposable view state, not the source of truth.
Rerendering or evicting an image therefore need not invalidate the text range.
=yunge-reader-copy-selection= copies resolved text or asks the driver for
=selection-text=.

A search result uses the same stable endpoints, but its transient highlight is
independent of the copy selection.  Search preview can therefore move and
repaint without changing the text copied from the logical selection.  The
distinction also leaves room for later decoration layers whose durable
records use the same position contract.

For PDF, =unit= is a zero-based page and =offset= is PDFium's zero-based
character index.  A selected range includes both endpoint characters and is
independent of drag direction, including when the drag crosses page slots.
The helper returns Unicode, loose character bounds, and optional oriented
quadrilaterals in canonical PDF points.  Emacs performs polygon hit testing
locally, stores only the stable endpoints, and asks PDFium to resolve the exact
range text.  Missing or malformed quadrilaterals fall back to bounds.
Cross-page copy preserves each exact page fragment and inserts one newline at
every page boundary.

The same boundary can carry later annotations.  Durable annotation data can
store document identity, stable endpoints, quoted text, color, and provenance
outside the renderer.  A PDF backend may additionally write native PDF
annotations, but a PDFium object handle must never be the only durable anchor.
No note-taking or annotation storage is part of the current milestone.

* Continuous roll, zoom, and rendering

Every reader buffer has one of three zoom modes:

- =fit-width= resolves scale from the visible content width;
- =fit-page= resolves scale from both viewport dimensions; and
- =manual= uses an explicit scale between configured bounds.

Opening returns canonical geometry for every page before rasterization.  Emacs
creates one stable buffer slot per page and gives each slot a correctly scaled
space placeholder.  Normal buffer scrolling therefore traverses the complete
document even though most pages have no live image object.

The adapter rasterizes only pages visible in a live window and a configurable
number of neighboring pages.  When a page leaves every window, its display
returns to the equal-size placeholder while its immutable cache path remains
available for reuse.  Navigation moves to an existing slot rather than
rebuilding the buffer, so logical positions and window anchors remain stable.

The chosen zoom maps each page to a pixel width between 16 and 8192.  A render
key includes the file's canonical name, size, modification time, page, width,
PDFium API, and native source build ID.  The helper derives the output path
from that 64-character key; an Emacs client cannot ask it to overwrite an
arbitrary path.  Page and width keyed results prevent an obsolete completion
from replacing a different page or scale.

The rendered-page cache starts pruning only after its recognized files exceed
=yunge-reader-cache-max-bytes=, which defaults to 1 GiB.  It then removes the
oldest entries until =yunge-reader-cache-target-bytes=, 768 MiB by default.
A cache hit best-effort updates the file modification time, so eviction
approximates LRU without a second cache index.  The helper operates only on
ordinary files named by exact render keys.  It never removes unknown files,
temporary files, directories, or symbolic links.

Text geometry is cached by page because it does not change with zoom.  After
a click or drag, Emacs embeds each visible selected PNG in an SVG and projects
that page's part of the logical range over it.  Rotated characters use SVG
polygons; older or exceptional geometry uses rectangles.  The source PNG
cache remains independent of ephemeral selection paint.

Document search is cooperatively paged.  One native request scans at most a
configured number of document units and returns a bounded match list plus the
first unscanned stable position.  Emacs stops after the first useful batch and
requests another only for repeat navigation.  An obsolete query generation
cannot publish results, and each native batch is short enough to let render
requests run between batches.

The PDF adapter requests text geometry only for ordinary visible prefetch or a
target search page.  It projects the first drawable match character into
display pixels, then adjusts window vertical and horizontal scrolling.  The
match stays correctly anchored across zoom changes because its source of truth
is the PDFium page and character range, not the image or buffer position.

* Native service lifecycle

The helper stays alive while documents are open, retaining parsed PDF state
and avoiding process startup for every page.  It remains owned by Emacs:

- =M-x yunge-reader-native-start= starts it explicitly.
- =M-x yunge-reader-native-stop= requests graceful shutdown, then enforces a
  deadline.  A prefix argument terminates it immediately.
- =M-x yunge-reader-native-restart= replaces it after graceful shutdown.
- =M-x yunge-reader-native-status= reports state, clients, paths, PDFium API,
  and native build identity.
- =M-x yunge-reader-cache-prune= prunes cached pages while no Reader document
  is open.

PDF documents acquire a service lease at open and release it after their
native =close= response.  Releasing the last lease schedules configurable
idle shutdown.  At the end of that delay, Emacs asks the helper to prune the
cache before shutting it down.  A new lease acquired during pruning prevents
shutdown.  The helper independently refuses pruning while it has an open
document, so Lisp reference counting is not the sole safety boundary.  Setup
refuses to interrupt active reader documents.

The helper also exits when stdin reaches EOF.  This covers forced Emacs exit
where Lisp cannot complete an ordinary request.  =kill-emacs-hook= sends a
best-effort shutdown without delaying editor exit.  The helper does not spawn
grandchildren.

Every startup begins with a =ready= message containing protocol version,
source build ID, PDFium API, and capabilities.  Emacs queues requests until it
validates all four.  Request IDs match asynchronous responses to callbacks.  A
crash fails all outstanding callbacks and permits at most one automatic
restart while a component retains the service.  The wire format is documented
in [[file:../native/yunge-reader/README.org][the native protocol document]].

* Setup and PDF engine

The tracked manifest pins PDFium =151.0.7881.0= and records a SHA-256 for x64
and arm64 assets on Windows, Linux, and macOS.  Setup performs these steps:

1. Select the asset matching the Emacs operating system and architecture.
2. Download into a private directory below =var/yunge-reader/setup/=.
3. Hash literal archive bytes and require the committed SHA-256.
4. Reject absolute, parent-traversing, drive-qualified, or backslash paths.
5. Extract only the library, version, top-level license, and dependency
   licenses into staging.
6. Parse and verify the four-component upstream version.
7. Atomically publish under =var/yunge-reader/pdfium/7881/=.
8. Build the locked Rust helper and load PDFium in a smoke test.

An invalid prior installation is renamed for inspection rather than deleted.
Normal document opening never downloads or compiles dependencies implicitly.

=pdfium-render= is a Rust API wrapper, not a PDF engine implemented in Rust;
the dynamic PDFium library is still required.  Building PDFium from Chromium
source is much larger than an editor setup transaction.  Normal setup uses a
pinned cross-platform binary release.  A maintainer CI recipe can later build
the same PDFium revision from source and publish hashes without changing the
client-side verification model.

The native protocol remains an engine boundary.  A pure-Rust engine can become
another backend after it meets the same rendering, encryption, text geometry,
selection, and annotation conformance tests.

* Next PDF slices

The next implementation slices should add, in order:

1. back and forward jump-history integration;
2. document outlines and internal or external links; and
3. annotation anchors and independent decoration layers.

* Testing

ERT tests cover driver precedence, asynchronous cleanup, zoom, logical
selection, native lifecycle, strict setup validation, PDF request mapping,
lease balance, fit calculations, stable roll slots, visible-page
virtualization, prefetch bounds, text caching, cross-page hit testing, copying,
rotated polygon painting, rectangle fallback, bounded search continuation,
stale search rejection, independent match painting, precise match scrolling,
canonical viewport capture, cross-scale place restoration, page clamping,
deferred window restoration, failed-open place protection, rejected restores,
keyed render completions, cache limits, prune-before-stop ordering, and lease
races.  Rust tests cover the handshake, strict parameters, safe cache
eviction, Unicode literal matching, byte-to-PDFium-index mapping, search
cursors and limits, regular and singular-angle quadrilateral recovery,
cross-page inclusive ranges, protocol errors, shutdown ordering, and EOF.

The integration path installs the pinned Windows library through the public
setup command, runs its =pdfium-info= smoke test, opens a five-page A4 fixture,
checks all page geometries, renders neighboring pages, closes the handle, and
shuts down.  It also extracts 1,938 indexed characters from the first page,
selects =3..14= in either direction, copies =Introduction=, and paints the
selection as SVG.  A second integration selects across the first two pages,
verifies the explicit page separator, paints both slots as SVG, then confirms
that an offscreen page returns to a same-size placeholder.  Rendered pages
have been compared visually with Poppler.  A generated fixture with 0, 30, 45,
and 90 degree text verifies native quadrilaterals, local hit testing, and
polygon highlights against the rendered glyphs.

A real PDF search check finds case-sensitive =SLIME= at offsets =0..4= in the
reference-card fixture.  A case-insensitive =compile= query returns two bounded
results, resumes at cursor =1485= without duplication, and returns the final
match before reporting =done=.
