* Reading notes and maintaining the index

Org files are the source of truth. SQLite stores a derived index; reading a
note must not require an open database or start the native file monitor.

=fangcun-model.el= defines the records exchanged by parsing, indexing, and
queries. It has no live state. =fangcun-org.el= reads Org content into those
records, and =fangcun-store.el= stores and queries them through SQLite.
=fangcun.el= coordinates configured roots, synchronization, and interactive
commands. The MCP tools use the same index and note operations as the Emacs
commands.

=fangcun-org-read-file= accepts a normalized yiyu and a file path. It returns
a plist containing =:nodes= and =:links= from the saved file. An unmodified
visiting Org buffer can supply that content only while its recorded file
modification time matches the file on disk. Unsaved edits and stale buffers
must not enter the index or replace the saved text shown in backlink previews.

=fangcun-org-read-buffer= accepts a buffer, a normalized yiyu, and a file name
relative to that yiyu. It reads the buffer's current content, including
unsaved edits. Both reading operations inspect the whole document while
preserving an existing buffer's point and narrowing.

* Node and link meaning

A file or heading becomes a node through its Org =ID= property. Text that
looks like an ID inside a source block or another drawer is not a node.
Titles are plain display text; aliases come from =ALIASES=, and tags follow
Org's inheritance settings.

An ID link belongs to its nearest enclosing node. A link's =::search= suffix
selects a location within the target; it is not part of the target node ID.
The reader normally omits links without an owning node. Its optional
=include-unowned= argument retains them so graph checks can report them.

Positions and line numbers describe the content that was read. They can
become stale after an edit. Node navigation resolves an ID again in the
destination buffer rather than treating an indexed position as permanent.

* Writing and querying the index

The storage module accepts model records and already-parsed data. It does not
read Org files, choose configured paths, or manage synchronization sessions.
Writes and metadata checks share a connection opened by
=fangcun-store-call-with-database=. It takes an explicit database path, prepares
the schema when new, and closes the connection when the callback returns or
signals an error. SQL and transaction handling belong inside the storage module.

Each parsed file is a pair of a =fangcun-file-state= and the =:nodes= / =:links=
plist returned by the Org reader. =fangcun-store-replace-files= receives these
pairs and deleted-file keys of the form =(yiyu-id . relative-file)=. It removes
all affected entries before inserting their replacements in one transaction,
so an ID can move between files within a batch. Duplicate IDs roll back the
whole batch. Single-file updates use the same operation.

The coordinator reads every changed file before asking the store to write.
=fangcun-store-rebuild= writes the complete parsed set to a temporary database
beside the destination, closes it, then replaces the destination. Parsing or
insertion failures leave the previous index intact.

File entries own their nodes, aliases, tags, and outgoing links, including an
entry for an Org file with no nodes. Modification time and size detect saved
changes; rebuilding parses every file when those checks miss a change. Link
targets may be unresolved or outside configured note roots, so deleting a
target does not remove incoming links.

Node and backlink queries take a database path and manage their own connection.
They return model records with titles, aliases, and tags ready for callers,
without scanning notes or starting a session.
Grouped backlinks identify each source node and its first occurrence; occurrence
queries retain every link position.

** Applying file events

File events name the paths to reconcile; they do not describe the final note
contents. Read those paths from disk when processing the batch, and remove
entries for paths that no longer exist. Emacs rename and delete operations
submit their affected paths together as well.

Full scans and native event batches require every configured root to exist.
Check roots before resolving event paths: =file-in-directory-p= returns nil
for a missing directory, which would silently discard its events. A missing
root stops the batch with a warning and leaves the index unchanged.

Atomicity covers one batch. Separate saves can still expose a temporary
duplicate ID, for example when a destination is saved before the source of
a moved node. After correcting the saved files, run =fangcun-db-sync= to
reconcile the whole index. Automatic failures warn without retrying in a loop.

* Synchronization sessions

A session owns a synchronized root configuration, helper processes, and queued
file events. Commands prepare the session before using the index; changing a
root's ID, name, or path requires synchronization with the new configuration.
Database queries such as =fangcun-node-list= read the stored index directly.

=fangcun--stop-session= ends that ownership: stop helper processes, cancel
the idle timer, discard pending events, and reset monitor recovery state.
Changing roots or rebuilding an active session stops it before scanning.
Only a successful synchronization activates the new session. If it fails,
the previous database stays available without continuing its old monitoring.

Detach a process before terminating it so its callbacks cannot restart it or
submit events. Stopping only the monitor for a restart or helper rebuild keeps
the session active. A scan may itself start a helper build, so session cleanup
must precede the scan rather than canceling that new build afterward.

Disabling the native helper stops its processes and clears queued events but
keeps the synchronized session. Emacs saves and explicit updates can still
write the index. Use =setopt= or Customize to apply this preference immediately;
an ordinary assignment is picked up on the next =fangcun-db-sync=.

Executable availability and the user's preference are separate facts.
Automatic scanning, monitoring, and building respect the preference. An
explicit =fangcun-native-build= can build while the helper is disabled; its
result describes the build, and success does not enable monitoring.

* Verification

Run the Fangcun Lisp checks from the repository root:

#+begin_src sh
emacs --batch -Q -L test -l yunge-test-runner -- --suite ert --module fangcun
#+end_src

Verify parser changes through returned nodes and links, and indexing changes
through queries or displayed results. Include saved versus unsaved content
when changing file reads. Do not test internal implementation details.

See the [[file:development.org][development guide]] for static checks and the full repository gate.
