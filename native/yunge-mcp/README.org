#+title: Yunge MCP native bridge

* MCP transport

With no arguments, =yunge-mcp= is a stdio Model Context Protocol server. An MCP
client starts it as a child process and exchanges one JSON-RPC message per
line. Standard output is reserved for MCP messages, including request errors.
Startup diagnostics use standard error.

Tool descriptions and implementations live in Emacs.  For each =tools/list=
or =tools/call= request, the executable invokes =emacsclient= with a fixed Lisp
form and passes its source build ID followed by the bridge request as separate
process arguments.  The request is ASCII Base64 containing UTF-8 JSON.  Emacs
rejects an installed helper whose build ID differs from the tracked source and
directs the user to run =M-x yunge-mcp-install=.  This avoids platform
command-line encoding loss and never constructs Lisp source from tool input.

The internal request is a JSON object with an =operation= member:

#+begin_example
{"operation":"list-tools"}
{"operation":"call-tool","name":"fangcun_locate_node",
 "arguments":{"id":"node-id"}}
#+end_example

Emacs returns a base64-encoded JSON object because =emacsclient --eval= prints
its result as a Lisp string.  Successful and failed responses have these
forms:

#+begin_example
{"ok":true,"value":{}}
{"ok":false,"error":{"type":"user-error","message":"..."}}
#+end_example

The =value= field is required on success. For =list-tools= it contains an
array of tool descriptions; for =call-tool= it must contain an object.
On failure, =error= supplies the Emacs condition type and its message.

Successful tool calls publish that object as =structuredContent= and the
same JSON as a text block in =content=, following the
[[https://modelcontextprotocol.io/specification/2025-11-25/server/tools#structured-content][MCP structured content format]]. Collection results belong in a named field:
=fangcun_list_yiyus= returns ={"yiyus": [...] }=, with an empty array when
no roots are configured. A non-object tool result returns JSON-RPC
=-32603= instead of an invalid =structuredContent= value.

** Errors and cancellation

The MCP handler distinguishes a failed tool from a failed bridge, following
the [[https://modelcontextprotocol.io/specification/2025-11-25/server/tools#error-handling][MCP error model]]:

| Failure | MCP response |
|---------+--------------|
| Unknown tool (=yunge-mcp-unknown-tool= from Emacs) | JSON-RPC =-32602=, invalid parameters |
| Tool argument validation, note conflicts, or other tool execution errors | Tool result with =isError: true= |
| Cannot run or connect through =emacsclient=, nonzero exit, or malformed response | JSON-RPC =-32603=, internal error |

=tools/list= failures return a JSON-RPC internal error because no tool is
being executed. Request errors leave the MCP connection available for later
requests.

When a client cancels a request, the handler stops waiting and terminates its
=emacsclient= process. The SDK suppresses that request's response. Closing
standard input ends the MCP session; the SDK allows pending requests a short
drain period before the bridge exits and terminates remaining child processes.

Stopping =emacsclient= does not undo an evaluation already sent to Emacs.
A creation operation may have saved a file even when its response is lost.
Inspect the target file before retrying; the bridge never retries requests
automatically.

* Connection settings

The installed server reads =../runtime.json= relative to its =bin=
directory.  The manifest records the exact =emacsclient= executable and the
arguments that select Yunge's Emacs server:

#+begin_example
{"version":1,
 "emacsclient":"D:/softwares/emacs/bin/emacsclient.exe",
 "connectionArguments":["--server-file","C:/path/to/server"]}
#+end_example

=M-x yunge-mcp-install= regenerates this machine-local file.  For development
and diagnostics, =YUNGE_MCP_RUNTIME= selects another manifest,
=YUNGE_EMACSCLIENT= overrides its executable, and
=YUNGE_EMACS_SERVER_FILE= overrides its connection arguments.

* Edit Codex configuration

=yunge-mcp edit-codex-config= processes one JSON request from standard input
and exits. It uses neither the runtime manifest nor an Emacs connection.
The request names the executable to register and contains the existing TOML:

#+begin_example
{"program":"D:/Yunge/yunge-mcp.exe",
 "configuration":"[mcp_servers.yunge]\ncommand = \"old\"\n"}
#+end_example

An empty configuration string creates a new document. The command replaces
the whole =mcp_servers.yunge= entry with =command= and an empty =args= array.
It accepts ordinary and inline server tables, preserving unrelated settings.
Invalid TOML or a non-table =mcp_servers= value fails without producing an
updated configuration.

On success, standard output is one JSON object with a string =configuration=
field containing the updated TOML. On failure, the process exits nonzero and
writes a diagnostic to standard error. Both input and output use UTF-8.
The command does not read or write client files; the caller replaces the file
only after validating a successful response. See [[file:../../doc/yunge-mcp-development.org][Yunge MCP development]] for
the Lisp caller and its file-writing guarantees.
